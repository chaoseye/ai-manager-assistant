# Записанные ответы для mock-режима

Файлы здесь использует `MockLLMClient` (`LLM_MODE=mock`): если текст нового обращения совпадает с полем `match` (без учёта регистра и пунктуации), возвращается `suggestion` из файла. Для остальных обращений mock ищет похожий вопрос в `faq.yaml`, а если не находит — отвечает «уточню» с `needs_human=true`.

Откуда ответы (поле `model`; нет поля — составлен вручную):

| Файл | Сценарий | Ответ |
|---|---|---|
| `01`–`06` | цена с монтажом, вне базы знаний, жалоба, торг, отказ от допродажи, prompt-injection | **Grok 4.7** через шлюз, 29.09.2026 — настоящие ответы модели, без правок |
| `07` | после покупки | вручную: ответ Grok не прошёл проверки ядра (предложил допродажу недовольному клиенту, проверка её сняла), а в mock-демо ошибка модели не должна выглядеть нормой |
| `08` | проверка цен | вручную, с **намеренной ошибкой** в цене: показывает, как проверка ловит сумму, которой нет в базе знаний |

На странице в «Технических данных» у записанного ответа видна модель: `grok-4.7 (запись)`.

Перезаписать ответы другой моделью (нужны `LLM_MODE=live` и доступ к модели; один платный запрос на сценарий):

```bash
python -m evals.record_scenarios --provider grok
python -m evals.record_scenarios --provider kimi --only complaint,after-sale
```

Запрос собирается так же, как на демо-странице. Ответ сохраняется, только если проходит проверки ядра без предупреждений; `08-price-check` не перезаписывается.

Формат файла:

```json
{"id": "…", "match": "текст обращения", "model": "grok-4.7", "recorded_at": "2026-09-29", "suggestion": { …Suggestion… }}
```
