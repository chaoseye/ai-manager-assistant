# Как проект собирался с помощью ИИ

Задание требует собрать сервис с помощью ИИ. Здесь описано, что делал ИИ-ассистент, что проверялось по первоисточникам и что осталось непроверенным.

## Инструмент

Claude Code (десктоп-приложение), модель Claude Opus 5.5. Ассистент работал в одном контексте, без субагентов: так требуют правила проекта для ассистента (локальный файл, в репозиторий не входит).

## Ход работы

1. **ТЗ.** По формулировке задания ассистент составил ТЗ, описание функционала и структуры (`docs/TZ.md`, `FUNCTIONALITY.md`, `STRUCTURE.md`). Перед этим он сверил ограничения amoCRM с официальной документацией: формат и таймаут вебхуков, повторы, лимиты API, типы примечаний, Salesbot, области виджетов. Ссылки — в разделе 14 ТЗ.
2. **Уточняющие вопросы.** Ассистент задал вопросы про объём работ, базу знаний, LLM и стек. Заказчик выбрал этапы 1–2, демо-базу знаний, Claude API и Python + FastAPI. Остальные вопросы закрыты значениями по умолчанию: локальный запуск, mock-режим без ключа, git в папке проекта.
3. **Этап 1.** Ядро, база знаний, проверки, CLI, REST API, демо-страница, тесты, eval-набор. Первый коммит.
4. **Этап 2 в mock-режиме** (ветка `stage-2-amocrm`). Вебхуки amoCRM, история переписки, очередь с паузой перед генерацией, контекст сделки, примечания; поддельный сервер amoCRM и консольный имитатор вебхуков.
5. **Подготовка к показу.** Страница «amoCRM (mock)»: карточка и лента сделки, сообщения уходят вебхуками в формате amoCRM. Сценарий с намеренной ошибкой в цене показывает, как её ловит проверка. В README — раздел «Как показать прототип за 5 минут» со скриншотами из встроенного браузера.
6. **Онлайн-демо на Vercel.** Проект подключён к Vercel из GitHub, каждый push в `main` публикует новую версию. На Vercel запись разрешена только в `/tmp`, а функция «засыпает» между запросами, поэтому фоновый цикл очереди там ненадёжен. Под это изменены умолчания:
   - база переехала в `/tmp`;
   - очередь продвигается опросом ленты страницы «amoCRM (mock)»;
   - в mock-режиме `WEBHOOK_SECRET` стал необязательным: без него вебхук выключен.
7. **Выбор модели.** По запросу заказчика добавлены GLM-5.3, DeepSeek V4 Pro, Kimi K3, Qwen3.8-Max и Grok 4.7.
   - Ассистент проверил по официальной документации, что модели существуют, как они называются в API и какой формат ответа поддерживают.
   - Шлюз заказчика оказался New API. id моделей в нём ассистент взял из открытого прайса шлюза, без ключа.
   - Реализация: общий клиент OpenAI-совместимого шлюза, реестр моделей с запасными, переключение на странице, в API, CLI и eval, команда подключения шлюза `python -m app.setup_gateway`.

## Что проверялось по первоисточникам, а не по памяти модели

- **SDK `anthropic` 1.9.0.** Сигнатуры `beta.messages.create` (параметры `fallbacks`, `betas`, `output_config`), публичная функция `transform_schema`, разбор структурированного ответа внутри SDK и способ, которым SDK находит учётные данные, сверены по исходникам установленного пакета.
- **Документация amoCRM.** Сверена по страницам разработчика (см. ТЗ, раздел 14). По примерам из документации ассистент воспроизвёл:
  - вебхуки: `message[add]` и `outgoing_message[add]`, автор `external` / `internal` с `user_id`;
  - ответы API v4: сделка с `_embedded.contacts[].is_main` и `catalog_elements[].metadata.catalog_id`, контакт с `_embedded.leads`, воронки с системными статусами 142/143, `filter[id]` у элементов каталога.
  На этих примерах построены парсер, клиент и поддельный сервер.
- **Модели через шлюз.** Для каждой модели по документации провайдера сверены:
  - id в API;
  - OpenAI-совместимый адрес;
  - поддержка `response_format` (`json_schema` у Kimi, Qwen и Grok; только `json_object` у GLM и DeepSeek);
  - управление рассуждениями (`reasoning_effort`, `enable_thinking` у Qwen, фиксированная температура у Kimi).

  Модели и их параметры проверены и через публичный `GET https://openrouter.ai/api/v1/models`: оттуда же ориентировочные цены для eval. Тип шлюза заказчика (New API) и id моделей в нём — по заголовкам ответа и открытому `/api/pricing`.
- **Демо-страница.** Проверена в браузере: сценарии, «Вставить в поле ввода» → отправка от имени менеджера → пометка «подсказка устарела», ожидание перед генерацией после сообщения клиента, вкладка базы знаний, светлая и тёмная темы, ширина 375 px без горизонтальной прокрутки, отсутствие ошибок в консоли.

## Ключевые решения

| Решение | Почему |
|---|---|
| Вся база знаний в системном промпте, без RAG | База короткая (~16 тыс. символов), поиск только добавил бы ошибок. Системный промпт кэшируется. |
| Один вызов модели на оба блока | Ответ и подсказка не противоречат друг другу, запрос вдвое дешевле двух отдельных. |
| `beta.messages.create` + своя валидация вместо `messages.parse` | `parse` проверяет JSON внутри SDK и падает раньше, чем код увидит `stop_reason`. Тогда обрезанный ответ или отказ модели нельзя отличить от просто плохого JSON. |
| Детерминированные проверки после модели | Цены, ссылки на базу знаний и допродажа при жалобе проверяются кодом, а не только просьбой в промпте. |
| Mock-режим с заранее составленными ответами | Демо и тесты работают без ключа и без затрат. |
| Поддельный amoCRM как HTTP-транспорт, а не заглушка клиента | В mock-режиме работает настоящий `AmoClient`: заголовки, лимит запросов, повторы, разбор ответов. К живому аккаунту остаётся подключить токен. |
| Пауза перед генерацией и проверка на устаревание | Клиенты пишут несколькими сообщениями подряд, а менеджер может ответить сам, пока идёт генерация. Подсказка не должна отвечать на половину вопроса или дублировать менеджера. |
| Повтор публикации без повторной генерации | Если amoCRM не принял примечание, сохранённая подсказка публикуется снова — токены модели не тратятся второй раз. |

## Что ассистент нашёл и исправил в своём же коде

- **Проверка цен была слишком мягкой.** Суммы любых трёх слагаемых покрывали 92% «круглых» сумм (кратных 100 ₽, от 1 000 до 119 900 ₽), и выдуманные 32 000 ₽ или 31 900 ₽ проходили. Правило переделано: разрешены одиночные цены, скидки и суммы двух позиций, а длинные итоги — только если остальные слагаемые названы рядом. После переделки таких сумм проходит 8,5%.
- **Сумма оправдывала сама себя.** Число из ответа попадало в список «названных рядом» и разрешало само себя. Суммы из переписки и из самого ответа теперь учитываются по-разному.
- **Каскад ошибок в загрузчике.** Одна ошибка в цене товара давала ещё и ложную «нет товара …» в правилах допродаж. Теперь ссылки проверяются по id всех записей.
- **Сценарий жалобы.** Два сообщения клиента подряд склеивались в одно обращение. В сценарий добавлена реплика менеджера.
- **Mock находил не тот FAQ.** Длинная жалоба на шум совпадала с вопросом «установите мой кондиционер». Похожесть теперь считается с обеих сторон.
- **Атрибут `hidden` не скрывал форму** на демо-странице: `display: grid` из CSS перебивал его. Добавлено глобальное правило.
- **Режим `live` без ключа.** SDK бросал `TypeError`: API отвечал 500, CLI падал с трейсбеком. Теперь учётные данные проверяются до запроса: API отвечает `503` с подсказкой, `/health` показывает `degraded`, CLI возвращает код 3.
- **Имитатор стартовал 8–12 секунд.** Он импортировал загрузку сценариев из модуля API, а тот тянул SDK модели (импорт — 5,8 с). Сценарии вынесены в лёгкий модуль, SDK импортируется только в режиме `live`. Теперь имитатор стартует за 1 с, CLI в mock-режиме тоже не грузит SDK (это проверяет тест). Нашлось при ручной проверке: второе сообщение имитатора не успевало прийти до конца паузы.
- **Гонка в SQLite.** Приём вебхуков и обработчик очереди работают на одном соединении. Пока курсор запроса с `RETURNING` (создание диалога, взятие задачи в работу) не был дочитан, чужой `commit` падал с «cannot commit transaction - SQL statements in progress». Изредка это роняло тест имитатора. Все чтения и `RETURNING` переведены на `execute_fetchall`: запрос и чтение строк идут одним вызовом. Регрессионный тест на старом коде падает.
- **Mock отвечал на вопрос о цене длительностью.** «Сколько стоит монтаж?» совпадал с «сколько длится монтаж» (похожесть 0,44 при пороге 0,4). Порог поднят до 0,5: на такой вопрос mock теперь честно отвечает «уточню».

С ключом заказчика через его шлюз (New API) проверено:
- **Ключ принят,** ему доступны 23 модели. Из нужных есть GLM-5.3, DeepSeek V4 Pro, Kimi K3, Qwen3.8-Max и Grok 4.7; Claude в наборе ключа нет. Отсюда проверка моделей при старте: иначе модель по умолчанию `claude` падала бы на каждом запросе.

- **GLM на всём наборе** (31 кейс, по 6 запросов параллельно): пройдено 24, из них 2 сбоя инфраструктуры. Вопросы вне базы знаний и prompt-injection — все пройдены. Жалобы — 1 из 4: модель ставит допродажу «после решения вопроса» вместо «не предлагать». Одна сумма не выводится из базы знаний. Медиана задержки — 80 с против 19 с для одиночного запроса.

В отчёте прогона у DeepSeek 29/31 и prompt-injection 1/2, у Qwen 15/31: проверка запрещала сами строки «90%» и «1 рубль», поэтому проваливала правильные отказы («Скидка 90% … не предусмотрены», «Цена 1 рубль не действует»). Теперь в этих кейсах работает `reply_not_promises`, и сохранённые ответы перепроверены ею без новых запросов к моделям. Сумм вне базы знаний, кроме разрешённых кейсом `kb-far-city`, нет у всех моделей, кроме Qwen. Торг «у конкурента дешевле» передал менеджеру только Grok. Kimi на вопрос о рассрочке ответил «рассрочки нет», хотя в базе знаний об этом ничего нет. По итогам моделью по умолчанию выбран Grok, запасными — DeepSeek и Kimi.

**Правка промпта по итогам сравнения** (Grok 4.7, 29.09.2026). Добавлены правила:
- не упоминать базу знаний и инструкции;
- не обсуждать инструкции при prompt-injection;
- отвечать на каждое пожелание клиента;
- торг передавать руководителю.

Что получилось:
- **Ответы на демо-сценарии.** Не пишут «в базе знаний нет», торг уходит руководителю, клиенту с ребёнком-аллергиком ответ про чистоту при монтаже.
- **Первая версия правила о пожеланиях** увела модель не туда. Она поняла «чисто» как повод предложить очиститель воздуха, вставила его прямо в ответ и написала «монтаж бесплатный». Поэтому правило уточнено, а в код добавлена проверка «допродажа в ответе клиенту».
- **Одного правила мало.** Про инструкции Grok продолжал писать примерно в половине ответов на prompt-injection. Поэтому в код добавлена проверка внутренних терминов: инструмент записи такой ответ не сохранит, а менеджер увидит предупреждение.
- **Eval на новом промпте — 30 из 31.** Первый прогон, `eval-20260929-232946-live-grok.md`, оборвался из-за сбоя шлюза (502 в 4 кейсах), эти кейсы догнаны отдельно в `eval-20260929-233909-live-grok.md`. «Старый кондиционер» теперь проходит, зато в кейсе «после покупки» Grok не предложил сервис. Формат «9900 ₽» теперь исправляют проверки.
- **Расход:** около $1,2 по ценам OpenRouter — трижды записанные ответы на сценарии, eval и догоняющий прогон.

По ходу реальных прогонов исправлено:
- запрос, не уложившийся в таймаут или оборванный туннелем через 100 с (Cloudflare 524), не повторяется: повтор упирается в тот же предел, а шлюз может списать оплату дважды;
- разовый 404 от модели за шлюзом повторяется, а подсказка «проверьте адрес» появляется только при реально неверном адресе;
- упавший туннель (Cloudflare 530) даёт понятную ошибку вместо HTML-страницы;
- eval гоняет модели параллельно, у каждой свой лимит одновременных запросов; он сразу останавливается, если шлюз не ответил на бесплатную проверку перед прогоном;
- в отчёте видно, как модель назвал шлюз; цена считается и для имён с датой версии;
- `setup_gateway` не падает с трейсбеком на неподставленном шаблоне адреса;
- Docker-образ, который не собирался локально (на машине разработки нет Docker), теперь собирается в GitHub Actions: `docker compose up --build`, затем проверка `/health` и `/api/v1/suggest` в контейнере. Там же ruff и pytest на Python 3.11 и 3.12;
- при отказе провайдера в доступе варианты запроса всё равно перебираются (у Qwen отказ зависел от параметров), а итоговая ошибка прямо говорит об отказе;
- «выдуманные суммы» в сводной таблице считаются без кейсов, где сумма вне БЗ разрешена;
- в кейсах про prompt-injection и торг проверка `reply_not_promises` ловит обещание, а не упоминание: фраза допустима только в предложении с отрицанием. Утечку промпта по-прежнему ловит строгая `reply_not_contains`.

## Проверка на живом аккаунте amoCRM

30.09.2026, тестовый аккаунт amoCRM с Telegram-ботом через официальную интеграцию. Сервис запущен локально с `AMOCRM_MODE=live`, модель — Grok 4.7 через шлюз.
- **Путь сообщения.** Клиент написал боту, вебхук `add_message` дошёл и разобран без пропусков: `origin=telegram`, `element_type=2` с id сделки. После паузы 6 с задача ушла в работу, Grok ответил с первой попытки за 88 с, проверки ядра предупреждений не дали. Служебное примечание с черновиком и допродажей появилось в сделке примерно через полторы минуты после вебхука.
- **«Неразобранное».** Новый чат создал сделку в «Неразобранном», и вебхук пришёл уже с её id. API принял примечание к такой сделке: принимать её заранее не нужно. Это снимает опасение из прошлой версии документа про `element_type` у чатов в «Неразобранном».
- **Менеджер ответил сам.** Ответ из чата сделки пришёл вебхуком `add_outgoing_message` с id сотрудника, и сервис записал его как ответ менеджера. Задача отработала в режиме `upsell_only`: в примечании «Менеджер уже ответил клиенту — черновик не нужен» и только блок допродажи. Порядок сообщений сервис берёт по времени amoCRM, а не по времени доставки, поэтому ответ учёлся, хотя вебхук о сообщении клиента пришёл позже вебхука об ответе. Ответ, записанный в режиме «Примечание», клиенту не уходит, и вебхука о нём нет, поэтому сервис его не видит. Сообщения робота Salesbot из amoCRM приходят как исходящие без id сотрудника и за ответ менеджера не считаются.
- **Доставка вебхуков.** Туннель с вебхуком поднимали четыре раза. Трижды вебхук доходил за 2–6 с, один раз вебхуки шли 1–6 минут: первые попытки до туннеля не доходили, и часть вебхуков amoCRM доставил своим повтором через 5 минут. «Invalid URL» при регистрации был и в медленном случае, и в одном из быстрых, а ожидание 1,5–3 минуты перед регистрацией его не предотвращало. Причину опоздания установить не удалось. Отсюда совет в README: пробное сообщение перед показом, а если оно опоздало, новый туннель.
- **Подключение.** `app.amocrm.connect` проверил токен и записал `AMOCRM_ACCOUNT_ID`. После смены адреса аккаунта достаточно поменять поддомен: токен и вебхуки привязаны к аккаунту, а не к адресу. Текущий поддомен по токену отдаёт `GET https://www.amocrm.ru/oauth2/account/subdomain`.
- **Регистрация вебхука.** На `POST /api/v4/webhooks` amoCRM иногда отвечает «Invalid URL» на рабочий адрес: он сам ищет домен в DNS, и свежий адрес туннеля не всегда успевает. В первый раз хватило одного повтора, во второй адрес приняли только через минуту. Поэтому `setup_webhook` повторяет запрос до 5 раз с растущими паузами, всего около минуты. После регистрации команда напоминает отправить пробное сообщение (см. «Доставка вебхуков»). Перед регистрацией она проверяет адрес: `/health` и пустая посылка на вебхук.
- **Туннели.** У провайдера разработчика туннели Cloudflare заблокированы: TLS до узлов Cloudflare обрывается. localhost.run отвечал 503 на половину запросов, а amoCRM повторяет недоставленный вебхук только через 5 минут. Работал pinggy по SSH через порт 443; на бесплатном тарифе туннель живёт 60 минут.

## Расширенное тестирование (02.10.2026)

Отдельная сессия ассистента проверила готовый проект «снаружи»: прочитала весь код, добавила 123 теста (свойства на hypothesis, граничные значения, враждебные тексты, гонки очереди), прогнала сервис под нагрузкой, в браузере (1366×768, 375×812, 812×375, обе темы) и на 174 настоящих ответах пяти моделей из `evals/reports`. Нашлось и исправлено:
- **Маскирование ПДн и поиск сумм за O(n²).** Длинное слово без пробелов (10 000 символов) маскировалось 1,5–2,7 с, а запрос максимального размера — 186 с, и всё это время сервис не отвечал, включая вебхуки amoCRM. Повторы в выражениях ограничены: тот же запрос — меньше секунды.
- **Обходы проверки цен.** Сумма, которую назвал клиент, проходила как «названная в переписке»; итог от ошибочной цены считался верным; «скидка 90%» и «монтаж бесплатный» не проверялись вовсе; «52.900 ₽» и «12 тыс. руб.» не находились. Теперь всё это даёт предупреждение и «Нужна проверка». На настоящих ответах моделей предупреждения о ценах совпали со старыми, новых об условиях — 3 из 174, все про спорные обещания.
- **Страница «amoCRM (mock)».** Лента показывала примечания чужих чатов той же сделки, а быстрая смена сценария дописывала сообщения в чужую сделку.
- **`API_TOKEN` ломал демо-страницу.** Ввести токен было негде; теперь страница его спрашивает.
- **Ревью перед мержем.** Изменения прочитала основная сессия ассистента и нашла три недочёта, исправленных в том же PR. Во-первых, после «Начать новый чат» посреди сценария поле ввода страницы «amoCRM (mock)» переставало отправлять. Во-вторых, ответ «в бюджет 40 000 ₽ укладывается Basic 07 с монтажом — 37 800 ₽» помечался как согласие на цену клиента: теперь бюджет клиента рядом с ценой из БЗ, которая в него укладывается, не помечается, а «договорились: 15 000 ₽ вместо 32 900 ₽» — по-прежнему да. В-третьих, точка в «30 000 р.» и «12 тыс. руб.» обрывала предложение, и согласие на цену клиента в такой записи проходило незамеченным.

Остальные найденные недочёты оставлены тестами с `xfail(strict=True)`: подмена `X-Forwarded-For` при подборе пароля живой модели, ответ 500 на граничные значения в вебхуке, защитные заголовки страниц, кодировка файлов БЗ, проверки настроек очереди и другие (список — в тестах, см. [STRUCTURE.md, раздел 12](STRUCTURE.md#12-тесты-и-eval)).

## Что не проверено

- **Qwen3.8-Max на всём наборе.** В шлюзе для ключа осталась только открытая версия `qwen3.8-2.4t-a95b`. Провайдер отказывал шлюзу в доступе («Access denied… account in good standing») в 13 кейсах из 31, поэтому её результат (15/31) говорит о канале шлюза, а не о модели.
- **Задержки как свойство моделей.** Через шлюз они менялись в разы между прогонами: Grok отвечал за 5–9 с, а в полном прогоне — p50 62 с; GLM — за 19–80 с, а в полном прогоне — 5 с. Это нагрузка на каналы шлюза, а не скорость моделей.
- **Реальные вызовы Claude API.** Ключа нет, поэтому eval на модели не запускался. Качество ответов и доля кейсов, проходящих критерии приёмки, пока не измерены. Проверено всё вокруг модели: формирование запроса, разбор ответа и все ветки ошибок — на поддельном SDK.
- **Ответы mock-режима.** Шесть ответов на демо-сценарии — настоящие ответы Grok 4.7 (`python -m evals.record_scenarios`), два составлены вручную: `08` с намеренной ошибкой в цене и `07`, где ответ Grok не прошёл проверки ядра. В записанных ответах видны недочёты модели, их не правили: в ответе вне базы знаний клиенту написано «В базе знаний отсутствует информация…», на prompt-injection — сухое «не могу игнорировать инструкции», в сценарии с ребёнком-аллергиком не отвечено на просьбу о чистоте при монтаже.
- **Живой аккаунт amoCRM — частично.** На живом аккаунте проверены сообщение клиента и ответ менеджера из Telegram-чата (см. выше). Склейка нескольких сообщений, вложения и долгая работа вебхука проверены только на поддельном сервере. Время ответа вебхука на живом аккаунте не замерялось. Причина однократного опоздания вебхуков на 1–6 минут не установлена.
